## 排查：`serverpod start` 在 melos 工作区根目录执行时要求手动选择项目

**现象**：在 `/Users/coderxslee/workspace/flutter_web_admin` 下执行 `serverpod start --no-tui`，CLI 弹出
`Multiple Serverpod server projects found. Select one:`，候选是 `flutter_web_server` 与 `serverpod_crud`。

**结论：不是 `serverpod_crud` 的建包方式有问题，是 Serverpod 4.0 CLI 的项目发现判据过于宽松。**

判据源码：`~/.pub-cache/hosted/pub.flutter-io.cn/serverpod_cli-4.0.0/lib/src/util/directory.dart`
的 `isServerDirectory()` —— 全文只检查两件事：

1. 目录下存在 `pubspec.yaml`
2. `parsePubspec()` 后 `content.name == 'serverpod'`，**或** `content.dependencies` 含 key `serverpod`

完全**不检查** `config/`、`bin/`、`migrations/`、`.serverpod/` 这些真正的 server 标志物。
`serverpod_crud` 作为库包必须声明 `dependencies: serverpod`（内部要用 `BaseEndpoint`/`CrudService`），
因此被动命中，被误判为 server 项目。

**发现算法**（`lib/src/util/server_directory_finder.dart` 的 `serverpodDirectoryFinder`，按 tier 短路）：

1. 当前目录命中 → 直接返回
2. 否则搜子目录（**maxDepth = 2**）→ 有候选即 `_returnCandidates`（多个则抛 `AmbiguousSearchException`）
3. 再找同名兄弟目录（`*_flutter`/`*_client` → `*_server`）
4. 再向上逐级搜父目录（maxUpwardLevels=5，遇 boundary 停）
   注意：`.git` / 含 `workspace:` 的 pubspec / HOME 是 boundary，但**只影响第 3、4 步**，第 2 步不受限。

本工作区各包的实际判定：`flutter_web_server`（`serverpod: 4.0.0`）命中、`serverpod_crud`（`serverpod: '>=4.0.0 <5.0.0'`）命中、
`flutter_web_client`（只有 `serverpod_client`）不命中、`flutter_web_shared`（只有 `serverpod_serialization`）不命中、
根 `pubspec.yaml`（serverpod 只在 `dependency_overrides` 段，而 `content.dependencies` 只取 `dependencies:` 段）不命中。
→ 正好两个候选，与提示完全吻合。

**可用规避手段**（未改任何代码）：

- 在 server 目录内启动（首选）：`cd flutter_web_server && serverpod start --no-tui` —— 命中第 1 步快路径，不询问。
- 或显式指定目录：`serverpod start --no-tui -d flutter_web_server`（`--directory`/`-d`，相对路径按 cwd 解析）。
- 交叉验证：`serverpod start -d serverpod_crud` 会成功进入加载（因为 `isServerDirectory` 为真），
  但随后会在读不到 `config/generator.yaml` 等配置处失败 —— 可作为"它确实只是被误判"的佐证。
- **不要**靠改 `serverpod_crud/pubspec.yaml` 去"修"：库包代码真的依赖 serverpod，
  移到 `dev_dependencies` 编不过，移到 `dependency_overrides` 也绕不过（判据只看 `dependencies` 段，
  而 `dependencies` 又真的必须有）。这是 CLI 侧缺陷，不是建包方式的问题。

**顺带确认**：`--no-tui` 下这个交互式 select 能正常工作；源码 `start.dart:152-155` 专门注释说明
TUI 模式下必须在 TUI 接管终端（raw mode）**之前**解析 server root，否则 select 提示会被破坏。

## 排查：「Failed to connect to the database」+ 一堆随机端口的假象

**现象**：`serverpod start` 打印 `VM service proxy listening on ...` / `MCP server listening on ...` /
`Server running.` 之后，开始 `ERROR: Failed to connect to the database.` +
`SocketException: Connection refused, address = localhost, port = 50775`（然后 50867、50943… 每次重试端口都变），
`Retrying to connect to the database in 10 seconds.` 无限循环。警告里打印的配置却是 `database port: 8090`。

**结论：两个独立的坑叠在一起。**

### 坑 1（假线索）：Dart 的 `SocketException` 报的是**本地临时端口**，不是目标端口

`address = localhost, port = 5xxxx` 里的 5xxxx 完全无意义，**服务端一直在老老实实连配置里的 8090**。
实测佐证（`/tmp/port_probe.dart`，连 8090 和 8099 两个都没人听的端口）：

```
FAILED localhost:8090  -> SocketException: ... address = localhost, port = 58090
FAILED localhost:8099  -> SocketException: ... address = localhost, port = 58093
```

每连一次本地临时端口就换一个，所以"端口随机递增"纯属幻象。**以后看到 DB 连接错误里的端口和
`config/*.yaml` 对不上，不要怀疑配置，直接按"端口没人听"去查。**

### 坑 2（真原因）：`serverpod start` 不会自动拉起本项目的 Postgres

直接原因是 8090 上没有任何进程监听：容器 `development-postgres-1` 在 **2026-09-22 17:24** 被优雅停止
（日志 `received fast shutdown request` + exit 0，不是崩溃；多半是 Docker Desktop 退出或重启机器），
之后一直没起。数据卷 `development_flutter_web_admin_data` 完好，`flutter_web_admin` 库还在。

而 Serverpod 4 CLI 的 compose 自动制备（`_resolveStartDocker` → `_findComposeFile`）**只看 server 目录下**：

```dart
// serverpod_cli 4.0.0 源码（snapshot 内可见）
File? _findComposeFile(String serverDir) {
  for (final name in ['compose.yaml','compose.yml','docker-compose.yaml','docker-compose.yml']) {
    final file = File(p.join(serverDir, name));   // ← 仅 <serverDir>/，不递归、不看兄弟目录
    if (file.existsSync()) return file;
  }
  return null;
}
```

本项目 compose 在 `docker/development/docker-compose.yaml`（`<serverDir>/../docker/<runMode>/`），
于是 CLI 判定"没有 compose 文件"→ 静默跳过 Docker 制备 → 服务端就开始 10 秒重试死循环。
**`--docker` 也救不了**（它只影响"找不到 compose 时是否报错"，路径依旧找不到）。

**恢复手段**（已实际执行并验证）：

```bash
cd /Users/coderxslee/workspace/flutter_web_admin/docker/development && docker compose up -d postgres
# 验证：8090 出现 LISTEN；docker exec development-postgres-1 pg_isready -U postgres -d flutter_web_admin
#       -> accepting connections；psql -l 里能看到 flutter_web_admin
```

**顺带的健康度确认**：`config/development.yaml` 的 `database.port: 8090`、compose 的 `8090:5432`、
`config/passwords.yaml` 的 `development.database` 与 compose 的 `POSTGRES_PASSWORD` 三者一致，无需改配置。
唯一误导项是 `flutter_web_server/env/.env.development` 里写着 `POSTGRES_DB=book_store`（旧值），
但 compose 的 `environment:` 优先级高于 `env_file`，实际建的是 `flutter_web_admin`，目前无害。

## 优化方案设计（用户要求"先给方案，不改"）——已核实的机制事实

1. **Arco `Tree.selectNode()` 会派发 `select` 事件**，这点已读源码确认（不是推测）：
   `node_modules/@arco-design/web-vue/es/tree/tree.js` L661 `selectNode()` → `internalSelectNodes` →
   L388 `selectNodes()` → L318 `emitSelectEvent()` → `emit("select", newSelectedKeys, ...)`。
   所以 `index.vue` 的 `onSuccess` 里"`selectNode()` + 显式 `search()`"必然发出**两个完全相同的请求**
   —— 与日志里相隔 3~4ms 的两条 `queries=46` 精确对应。
   反面参考：`expandAll()` 走 `internalSetExpandedKeys`（L655 附近），**不**派发 `expand` 事件。
2. **`getUserList` 完全没有服务端分页**：`user_service.dart` 的 `SysUser.db.find(...)` 只有 `where` + `orderByList`，
   **没有 `limit/offset`**；`UserListRequest` 定义在 `flutter_web_shared/lib/src/models/requests/user/user_list_request.spy.yaml`，
   只有 tenantId / deptId / username / nickname / phone / email / status，**没有 page/pageSize**。
   前端 `useTable` 明明发了 `{page, pageSize}`（`useTable.ts:67`），但模型里没这两个字段 → 被静默忽略；
   `total` 靠 `res.total ?? records.length` 兜底（`useTable.ts:76`）→ 现状是**全表返回 + Arco 表格客户端切片分页**。
   所以"分页"只是前端假象，数据量一涨就是全表扫 + 全量传输。
3. `SysDept.parentId: int?, default = 0` —— 根部门用 **0** 而非 null；`sys_dept` 上已有
   `(tenantId, parentId, deleted)` 索引，BFS 的单次查询本身不慢，**贵在 45 次往返**。

**方案要点（待用户决定是否实施）**：B1 = `_collectDeptAndChildrenIds` 改一次查询 + 内存建树走树（45→1）；
F1 = 删掉 `onSuccess` 里那次冗余 `search()`（靠 `selectNode` 派发的 select 事件统一走 `onDeptSelect`，或加 guard 标志位）；
F2 = `useDept` 加请求级去重/缓存（消除 `UserFormModal` 常驻带来的重复）；F3 = `useTable` 改 `immediate:false`
（去掉那次立刻被覆盖的无 deptId 全量请求，需补 deptList 为空时的兜底 `search()`）；
B2（可选）= 真正做服务端分页，需给 `UserListRequest` 加 page/pageSize 并在响应里带 total。

   的分支（否则表格会一直空白）。
5. **`flutter_web_server/lib/src/generated/...` 四件套**由 `serverpod generate` 自动更新（端点签名未变，路由表未变，
   所以**不需要重启进程**，service 改动走热重载即可）。

### 关键判断依据（为什么 B2 选 `PageResponse` 而不是 `{records,total}`）

`gi_demo_admin/src/hooks/useTable.ts:76` 的 `total` 取值顺序是
`res.total（顶层） ?? (isPagedObject ? responseData.total : records.length)` —— 顶层优先。
`PageResponse<T>` 的结构正好是 `{code,message,page,pageSize,totalPage,total,data:[...]}`（`data` 是数组、`total` 在顶层），
天然命中；若改用 `{records,total}` 包裹式，`total` 会落到 `records.length`，分页直接退化成"当前页条数"。
另外 `http.ts` 的 `request()` resolve 的是 `res.data`（**裸响应体**），所以拦截器不会把 `total` 包进 `data` 里。
`PageResponse<T> extends CommonResponse`，端点仍是 `Future<CommonResponse> getUserList(...)`，签名与 Flutter client 都不用改。

### 验证结果 —— F3 由 HMR 重挂载自然取证

因为我改前端的几次保存会触发 Vite HMR → 组件重新挂载，日志里留下了"天然页面加载"的痕迹：

```

```

即：**F3 后每个页面实例只发 1 次 `getUserList`（带 deptId、queries=3）**，那条会被立刻覆盖的无 deptId 全量请求消失了。

而 `search()` / `refresh()` / `handleDelete()` 三条显式路径都直接或间接走 `getTableData()`，不受 `immediate` 影响。
