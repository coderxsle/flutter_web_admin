**方案**：沿用上游 Iconify 机制 + 恢复本地彩色图标（不引回旧依赖）。

- `computed` 由 `unplugin-auto-import`（`vite.config.ts` 的 `imports: ['vue']`）全局注入，写 `<script setup>` 时**不需要手动 import**；声明在 `src/auto-import.d.ts`。

## base_endpoint 的 update 入参契约（只读排查 + 非破坏性实测）

**入参形状**：`POST /user/update`，body 必须是 **`{"data": {...实体字段...}}`**。
参数名 `data` 来自 `BaseEndpoint.update(Session session, dynamic data)`，已确认注册在 `lib/src/generated/endpoints.dart:1391-1405`（生成器能扫到继承自 `BaseEndpoint` 的方法）。
实测：body 缺 `data` 键（或直接传实体对象）→ `HTTP 400 Missing required query parameter: data`；带了 `data` 则进入解码，形状正确。

**解码链**：`BaseEndpoint.update` → `decodeModel` → `meta.decodeModel`（`crud_entity_meta.dart:56`）→ `SerializationManager.deserialize<SysUser>(data, SysUser)` → `SysUser.fromJson`。
`__className__` 可带可不带（`protocol.dart:5656` 只有与期望类型不一致才走多态分支）。

**⚠️ 最大的坑：它是整行覆盖，不是部分更新**
- `updateRow` → `update(..., columns: null)` → `selectedColumns = (columns ?? table.managedColumns)`（`serverpod_database-4.0.0/lib/src/adapters/postgres/database_connection.dart:320`），而 `managedColumns => columns`（`concepts/table.dart:75`）。
- 生成 SQL：`UPDATE "sys_user" AS t SET "每列" = data."每列" FROM (VALUES ...) WHERE data.id = t.id` —— **所有落库列都会被写**。
- 后果：
  - 不传 `password` → 被写成 NULL（`password` 在 `SysUserTable.columns` 里，是落库列）。而前端根本拿不到该值（`scope=serverOnly` + `getDetail` 里 `copyWith(password: null)`）→ **通用 update 会直接清空用户密码**。这正是 `user_service.dart` 里那段被注释掉的定制 `update`（先查 existing 再逐字段改）存在的原因。
  - 不传 `createTime` → `SysUser.fromJson` 走 `createTime ?? DateTime.now()` → 创建时间被改成当前时间。
  - `deleted ?? false`、`status ?? 1`、`type ?? 2`、`isSuperuser ?? false`、`tenantId ?? 0`、`gender ?? 3` —— 缺谁就用默认值覆盖谁。
- 必填：`username`、`nickname` 在 `fromJson` 里是 `as String`（非空断言），缺了直接 500。

**前端现状**：`gi_demo_admin/src/apis/base.ts:43` 的 `update` 把 payload 写死了 —— 忽略传入的 `params`，永远提交 id=2（chen.yu）那份字面量；里面还带了 `roleIds`（不是 SysUser 字段，`fromJson` 会静默丢弃），且没有 `password` → 真调用会清掉 chen.yu 的密码。

### 补充：BaseEndpoint.update 是否支持「部分字段」payload —— 实测否定

用户问：以后继承 `BaseEndpoint` 的类直接用基类 `update`，能否支持 `{"data":{"id":2,"tenantId":0,"deptId":2}}` 这种只传部分字段？

**结论：不能。** 用临时探针脚本直接调 `SysUser.fromJson`（跑完即删）实测：

| payload | 结果 |
|---|---|
| `{id,tenantId,deptId}` | `_TypeError: type 'Null' is not a subtype of type 'String' in type cast`（缺 username） |
| `{id,tenantId,username}` | 同样 TypeError（缺 nickname） |
| `{id,tenantId,username,nickname}` | 解码通过，但 `password=NULL`、`authUserId=NULL`、`createTime=当前时间`、`gender=3`、`deptId=null`、`status=1` |
| 完整一行 | 全部正确保留 |

即：**根本没有 merge 这一步** —— `decodeModel` 是从 payload 造一个全新模型，不读 existing；再叠加 `updateRow` 的整行覆盖，缺的字段就是「用默认值/null 覆盖」。

**另一个坑（此前注释掉那段 update 的真正原因）**：不能在子类里把签名收窄成 `update(Session, UserRequest)` —— Dart 报
`error - invalid_override: 'B.update' isn't a valid override of 'A.update'`（`dynamic` 是 top type，收窄即非法覆写）。
所以自定义 update 必须**保持 `dynamic data` 形参**，在方法体内自己 `UserRequest.fromJson(...)`。

**三种可选修法（已提给用户，未落代码）**
- A 最小：子类保持 `update(Session session, dynamic data)`，体内解码成 `UserRequest` 再走定制 service（查 existing → 白名单赋值 → updateRow）。
- B 换方法名：`userUpdate(Session, UserRequest req)` → 路由 `/user/userUpdate`，但基类那个危险的 `update` 仍会被注册，藏不掉。
- C 改框架（治本）：`BaseEndpoint.update` 里做 merge —— `existing.toJson()` 与传入 map 做 `{...existing, ...provided}`（key 存在即覆盖，含显式 null），再 `decodeModel(merged)` 后 `updateRow`。这样所有实体都天然获得 PATCH 语义。注意 `toJsonForProtocol()` 不含 password，merge 要用 `toJson()`。

## 实现 BaseEndpoint.update2（方案 C，PATCH 语义）

**文件**：`flutter_web_server/lib/src/endpoints/system/base_endpoint.dart`（新增方法，未改动原 `update`）。

**实现要点**
1. 先取主键 —— **不能走 `decodeModel`**，部分字段的 payload 本来就缺必填字段，整体反序列化会先抛异常，拿不到 id。改成从原始 map 取：`service.idColumn(service.table)` 拿到列，同时兼容 `fieldName` / `columnName` 两个 key，用 switch 兼容 int/num/String。
2. 白名单校验：`knownFields` 取自 `service.table.columns` 的 `fieldName`，若请求里除主键外没有任何已知字段，直接返回失败并列出可用字段（避免字段名拼错时静默成功）。
3. `service.get(session, id)` 读基线（返回 `T?`，会自动按租户过滤 + 排除软删记录）。
4. `merged = {...existing.toJson(), ...provided}` 再 `decodeModel(merged)` → `service.update`。
   - **必须用 `toJson()`**：`toJsonForProtocol()` 不含 `scope=serverOnly` 的 password，会把密码合并成 null。
   - `existing.toJson()` 里带 `__className__: 'SysUser'`，与期望类型一致，不会触发多态分支，安全。
   - 显式传 `{"xxx": null}` 依然能清空字段（靠 key 是否存在判定）。
5. 全流程包 try/catch，字段类型不匹配等异常返回 `CommonResponse.failed('部分更新失败：…')` 而不是 500。

**已验证**：`serverpod generate` 后 `/user/update2` 与 ProductEndpoint 的 update2 都注册进 `endpoints.dart`；Flutter 客户端 `client.dart:423` 也生成了 `update2(dynamic data)`。`dart analyze` 仅剩原有的 doc-comment info。

**两个关键环境事实（踩过）**
- `serverpod generate` **必须用 `~/fvm/versions/3.44.4/bin/dart`（3.12.2）**：默认的 `~/fvm/default`（3.13.0）跑 CLI 会报 `Can't load Kernel binary: Invalid kernel binary format version (expected 138, found 130)`，因为 `~/.pub-cache/global_packages/serverpod_cli` 的快照是旧内核。
- **新增路由必须重启后端进程**。热重载只重载已存在方法的方法体（所以之前给 `getUserList` 加 `disabled` 是不重启就生效的），但路由表 `Endpoints()` 只在启动时构建一次 —— 生成后 `/user/update2` 仍返回 `Method not found in endpoint`，`touch` 文件强制重载也无效。**因此本次未能在真机跑完验证，等用户重启后补测。**

**待补测清单**（用户重启后执行）
1. `{"data":{"id":2,"deptId":5}}` → 应成功，且 username/nickname/password/authUserId/createTime 全部不变（可再调 `/user/update`… 不要，会毁数据；改回 5→2 还原）。

### update2 报 `No deserialization found for type named null` 的根因与修复

用户重启后测 `{"param":{"id":2,"deptId":5}}`，报：
`FormatException: No deserialization found for type named null`
（栈：`parseParameters` → `Protocol.deserialize` → `deserializeDynamicFieldValue` → `deserializeByClassName`）

**根因**：**Serverpod 4 的 `dynamic` 形参不能直接收普通 JSON 对象**。`parseParameters` 对 `description.type == dynamic` 会走
`Protocol.deserialize` 的 `if (t == dynamic)` 分支 → `deserializeDynamicFieldValue`，要求线格式是**带类型标签**的
`{"className":"Map","data":{"id":{"className":"int","data":2}, ...}}` —— 每个字段值还要再包一层。
直接传 `{"id":2,"deptId":5}` 时 `data['className']` 为 null → 抛该异常。

**注意**：改成 `Map<String, dynamic>` 形参**不能解决**。生成的 `protocol.dart` 分支是
`(data as Map).map((k,v) => MapEntry(deserialize<String>(k), deserialize<dynamic>(v)))`，
每个值仍走 `deserialize<dynamic>` → 报 `got int instead`。`Map<String, Object>` 也没有分支，会 fallback 到
`super.deserialize` 抛错。

**用探针脚本离线实测结论**（`tool/_probe_dynamic_param.dart`，跑完即删）：
| 传法 | 结果 |
|---|---|
| `deserialize<dynamic>({id:2,deptId:5})` | ❌ No deserialization found for type named null |
| `deserialize<Map<String,dynamic>>({id:2,deptId:5})` | ❌ got int instead |
| `deserialize<dynamic>({className:'Map',data:{id:{className:'int',data:2}}})` | ✅ 得到 `{id:2, deptId:5}` |
| `deserialize<String>('{"id":2,"deptId":5}')` | ✅ |

**修复**：把 `update2` 形参改成 **`String`**（JSON 对象文本），服务端 `jsonDecode` 后校验是 Map 再继续。
线格式变成 `{"param":"{\"id\":2,\"deptId\":5}"}`。

**顺带确认**：用户在文件里把形参名从 `data` 手动改成了 `param`（已保留其命名，未回退）。
客户端/前端调用要跟着用 `param` 这个 key。

**当前状态**：已 `serverpod generate`（`endpoints.dart` 里 `type: getType<String>()`，`flutter_web_client` 生成
`update2(String param)`），`dart analyze` 干净。**但服务端必须再重启一次** —— 路由表里存着旧的参数类型
`Map<String, dynamic>`，不重启会变成方法形参类型不匹配的中间状态。

### 补充：Map<String, dynamic> 其实可用，只是要求「每个值带类型标签」

用户追问「是不是只能传字符串？在方法体里第一时间转字符串也不行？」—— 分两块回答，并补做了实测：

**1. 方法体里转换没用**：异常发生在 `parseParameters`（`endpoint_dispatch.dart:169`），
早于 `methodConnector.call`。形参还没交到方法里就炸了，所以 `try/catch` 也拦不住。
判据：如果方法体执行过，会返回 HTTP 200 + `CommonResponse.failed` 的 JSON；实际是裸 500 + 栈，说明没进方法体。

**2. `Map<String, dynamic>` 是能用的**，只是线格式要求每个**值**带标签（我先把形参临时改回 Map、
重新 generate 让 `if (t == Map<String, dynamic>)` 分支回来之后再探的）：

| 形参类型 | 传裸对象 | 传「每值带标签」 | 传 JSON 文本 |
|---|---|---|---|
| `dynamic` | ❌ No deserialization found for type named null | ⚠️ 还要再套一层 `{"className":"Map","data":{...}}` | — |
| `Map<String, dynamic>` | ❌ got int instead | ✅ 可用 | — |
| `String` | ❌ is not a subtype of type 'String' | — | ✅ |

即 `{"param":{"id":{"className":"int","data":2},"deptId":{"className":"int","data":5}}}` 能让 Map 形参成功。
但前端要为此写递归加标签的 helper（还要处理 DateTime/UuidValue 的特殊编码），
比 `JSON.stringify` 一行代码麻烦得多，所以**仍然选 `String`**。

**3. 探针陷阱（重要）**：生成的 `protocol.dart` **只为 schema 里实际用到的类型生成分支**。
形参改回 `String` 后，`if (t == Map<String, dynamic>)` 分支直接消失 —— 此时再探 Map 会报
`DeserializationTypeNotFoundException: No deserialization found for type Map<String, dynamic>`，
这是「分支没生成」而不是「类型不支持」，两者别混淆。

**最终状态**：形参 = `String param`，已 generate（`type: getType<String>()`），`dart analyze` 干净，
`Map<String, dynamic>` 分支已随类型移除。仓库处于一致状态，等用户重启后端即可测。

## 前端接入 update2 的契约问题（只诊断，未改任何代码）

触发：用户问 `UserFormModal.vue:251` 用字符串调 `baseAPI.update`、「`http.post` 的 params 是不是应该支持
字符串/字典多种类型」理解得对不对。按约定只给结论 + 方案，等指令再动手。

### A. 「放宽入参类型」是错的方向（tsc 实测）
`string` 既不能赋给 `Record<string, any>` 也不能赋给 `object`：
```
error TS2345: Argument of type 'string' is not assignable to parameter of type 'UpdateParams'.
error TS2345: Argument of type 'string' is not assignable to parameter of type 'object'.
```
Serverpod 要的 body 是 `{"param":"<JSON 文本>"}` —— 外层必须是**对象**，字符串是 `param` 这个**字段的值**。
所以 `http.post(url, params?: object)` 保持 `object` 就够，不需要放宽成 `string | object`。
类型约束应写在 `DefaultP.UpdateParams`（**字段级收窄**）：`UpdateParams: { param: string }`。

### B. `JSON.stringify({param: submitData})` 是 bug（两个独立原因）
1. 把整个信封串成字符串 → body 成裸文本，服务端解出 `param` 是对象 → `Map is not a subtype of String`；
2. axios **0.27.2** 的 `transformRequest`：只有 `isObjectPayload || contentType==='application/json'` 才
   `setContentTypeIfUnset(headers,'application/json')`；字符串直接 `return data`，**不带 Content-Type**
   （读 `node_modules/axios/lib/defaults/index.js:73-86` 确认；0.27 里 `defaults.headers.post` 是空对象）。

正确写法：`baseAPI.update({ param: JSON.stringify(submitData) })`
→ body `{"param":"{\"id\":2,\"username\":\"chen.yu\",...}"}`。

### C. ⚠️ `baseAPI.update` 全局指向 `/update2` 打坏了另外几个模块
`getBaseApi`（`apis/base.ts:23`）被 **6 个模块**共用：person / dept / dict / menu / role / user。
后端端点基类实况：

| 端点 | 基类 | `/xxx/update2` 是否存在 |
|---|---|---|
| `UserEndpoint` | `BaseEndpoint` | ✅ 继承来的 |
| `ProductEndpoint` | `BaseEndpoint` | ✅ |
| `Dept` / `Role` / `Menu` / `Dict` Endpoint | 普通 `Endpoint` | ❌ 无路由 → `404 Method not found` |

而且 dept/role/menu/dict 的 `update` 是**各自重写**的，形参名是 `req` 而不是基类的 `data`：
`dept_endpoint.dart:22 update(Session, DeptRequest req)`、`role_endpoint.dart:62 update(Session, SysRole req)`。

三个现存调用点、两种坏法：

| 位置 | 现在传的 | 结果 |
|---|---|---|
| `views/crud/form/index.vue:148` | 裸对象 `form` | 缺 `param` → 400 |
| `views/system/dept/DeptFormModal.vue:133` | `{ req: submitData } as any` | 打到不存在的 `/dept/update2` → 404 |
| `views/system/user/UserFormModal.vue:251` | 字符串 | 类型错误 + body 形状错 |

### D. ⚠️ 用户编辑根本不该走通用 `update2`：`roleIds` 会被静默丢弃
`SysUser` 模型里**没有 `roleIds`**（`sys_user.spy.yaml` 只有 `postIds`）。角色存在 `sys_user_role`
关联表，由 `user_service.dart` 的 `_saveUserRoles` 维护，且**只在 `add` 里被调用过一次**。
`update2` 的字段白名单来自 `service.table.columns` → `roleIds` 不在其中 → 被丢掉。
后果：编辑弹窗里角色是必填项，用户改了角色 → 接口返回成功但**角色没变**（静默失败，最难查）。

正解：`user_service.dart:423-497` 有一段**注释掉的** `update(Session session, UserRequest req)`
（查 existing → 用户名查重 → `_saveUserRoles(clearExisting: true)` → 只赋传入字段 → `updateRow` →
`copyWith(password: null)`），`user_endpoint.dart:49` 的 override 同样被注释掉。两段放出来即可，
user 模块就完全不需要 `update2` 那套字符串参数。

### E. 同文件另外两个雷
- `submitData.isSuperuser = false` 在编辑分支也无条件发送 → 编辑任何超级管理员会把它降级
  （目前只靠「内置用户按钮禁用」这个 UI 层防护挡着）。
- `submitData.status = form.status ?? '1'` 的 fallback 是**字符串** `'1'`，而模型 `status` 是 `int`
  → 命中 fallback 时会 cast 报错。

### F. 「我改了但浏览器 payload 还是旧样子」的判定方法（已实测）
用户改成了 `baseAPI.update({ param: JSON.stringify(submitData) })`（源码确认无误），但浏览器 Network 里
看到的 payload 仍是 `{"param":{...}}`（param 是对象、无转义）。用本地起 http server 抓包实测 axios **0.27.2**
的实际网络行为，两种写法可**逐字节**区分：

| 写法 | Content-Type | body 长度 | body 特征 |
|---|---|---|---|
| A 旧：`JSON.stringify({param:submitData})` | `application/x-www-form-urlencoded` | 221 | `{"param":{"email":…}}`，`param` 是对象、无转义 |
| B 现：`{ param: JSON.stringify(submitData) }` | `application/json` | 257 | `{"param":"{\"email\":…}"}`，`param` 是字符串、有 `\"` 转义 |

用户贴的 payload 与 **A 逐字节相同** → 他看的是**旧代码发出的请求**（页面未重新加载 / HMR 没生效 /
DevTools 里是历史记录），不是源码没改对。
**结论：判断浏览器里那条请求属于新旧代码，看 `Content-Type` 最快** —— 字符串当 data 时 axios 0.27 的
`transformRequest` 直接 `return data`，保留 `defaults.headers.post` 的
`Content-Type: application/x-www-form-urlencoded`（`lib/defaults/index.js:9-11`、`:142-144`）；
对象 data 才走 `setContentTypeIfUnset(headers,'application/json')`。

顺带确认：`roleIds:[10]` 在这种 payload 下会被 `update2` 丢掉（见 D），所以修好形状后接口会返回成功但角色不变。

## 16:16 前端 `base.ts` 收敛成两个 update 方法（评审 + 实测）

用户把 `base.ts` 改成两个方法：
```ts
update(params: P['UpdateParams'])                { return http.post(`${baseUrl}/update`,  params) }
updateWithParamString(params: P['UpdateParams']) { return http.post(`${baseUrl}/update2`, {params: JSON.stringify(params)}) }
```
意图：`update` 给**目标端点自己重写了 update** 的场景（dept/role 等，body key 是 `req`）；
`updateWithParamString` 给走通用 `base_endpoint.update2` 的场景。

### ⚠️ 硬 bug：body key 写成了 `params`（复数），后端要的是 `param`
拿 admin 登录后实测 `/user/update2`（`--noproxy '*'`）：

| body | 实测结果 |
|---|---|
| `{"params":"{\"id\":999999,\"deptId\":2}"}` | **HTTP 400 `Missing required query parameter: param`** |
| `{"param":"{\"id\":999999,\"deptId\":2}"}`  | **HTTP 200 `{"code":50000,"message":"数据不存在或已删除：id=999999"}`** |

第二条同时证明：**后端已重启**、`update2` 的 `String param` 线上生效（不再有反序列化报错）、
业务逻辑真的跑到了 `service.get` 那一层。用 `id=999999` 是为了不写任何数据。

### 命名评审（结论：建议改名）
`updateWithParamString` 的问题不是长，而是**命名了「怎么编码」而不是「做什么」**：
1. 把 Serverpod 的形参名 `param` 和 Dart 类型 `String` 泄进前端 API 名。后端哪天换成带标签的 Map
   （技术上可行）名字立刻变谎言，而调用点一行都不用改。
2. 真正的语义差别是 **PATCH（只改传入字段）vs PUT（整行覆盖）**，不是 string vs Map。
3. 「update = Map 传参」只是表象：body key 其实取决于目标端点**有没有重写 update**
   （user/product 落到基类 → `data`；dept/role 自定义 → `req`）。
推荐 `updatePartial`（最推荐）/ `patch`；若坚持标编码用 `updateWithJsonString`，别用 `param`。

### 签名也该改
`P['UpdateParams']` 语义上是「整行」，而这是部分更新。建议 `DefaultP` 里单独加
`PartialUpdateParams?: Record<string, any>`，签名写成
`updatePartial(params: P['PartialUpdateParams'] & { id: Id })` —— 把「必须带主键」从服务端运行时
提前到编译期。注：user 模块目前**没有**声明 `UpdateParams`，两个方法现在都是
`Record<string, any> | undefined`，等于零约束。

### 仍未解决
用户编辑走 `update2` 时 `roleIds` 被静默丢弃（见 D）。已两次提议恢复
`user_service.dart:423-497` / `user_endpoint.dart:49` 里被注释掉的定制 `update`，等用户决定。

## 17:15 新增 `addByJsonParams` 并抽离公共逻辑（已落地）

背景：`add(Session, dynamic data)` 与 `update(Session, dynamic data)` 有同一个毛病 ——
`dynamic` 形参收不了普通 JSON 对象。用户要求补一个 `addByJsonParams`，并把两个方法的重复代码抽出来。

### 用户已自行改名
`update2` → **`updateByJsonParams`**，且形参名从 `String param` 改成 **`String params`**。
（所以前端 body key 用 `params` 现在是对的；之前我说「key 该是 param」是基于旧代码，
后端改名后已不适用。）生成代码当时还是旧的，已重新 `serverpod generate`。

### ⚠️ 关键约束：Endpoint 子类的**公开**方法会自动变成 HTTP 路由
实测 `/user` 生成的方法列表：
`userAdd, getUserList, getUserInfo, getUserRoutes, getDetail, resetPassword, addByJsonParams, add, getList, update, updateByJsonParams, delete, deleteBatch`
—— 凡是能表达出签名的公开方法都在里面。所以往 `BaseEndpoint` 上加辅助逻辑**必须用下划线私有**
（私有成员不会被扫描）。`decodeModel` 之所以没被注册，是因为它返回泛型 `T`、生成器表达不出来，
属于巧合而不是保证。

### 落地内容
**新文件** `lib/src/endpoints/utils/json_param_codec.dart`：
- `JsonParamFormatException` —— 中转异常，端点捕获后转成 `CommonResponse.failed('参数不合法：...')`
- `JsonParamCodec.decodeObject(String raw, {required String paramName})` —— jsonDecode →
  校验是 Map → cast，失败抛上面的异常。放在**非 Endpoint 类**里，顺带规避路由注册风险。

**`base_endpoint.dart` 新增私有辅助**（全部 `_` 前缀，不会变成路由）：
- `late final Set<String> _knownFieldNames` —— 字段白名单（`service.table.columns`；
  端点实例是启动单例，所以只算一次）
- `String get _idFieldName` —— 主键字段名，仅用于报错
- `Set<String> get _primaryKeyKeys` —— `{fieldName, columnName}`，取主键与排除主键**共用同一套 key**
- `({Set<String> known, Set<String> unknown}) _splitFieldNames(provided, {excludeKeys})`
  —— 把请求体的 key 分成认识的 / 不认识的
- `int? _extractPrimaryKey(provided)` —— 兼容 `2` / `"2"`
- `String _describeUnknownFields(unknown)` —— 拼报错片段

**两个公开端点方法**：`addByJsonParams` 与（重构后的）`updateByJsonParams`。
共用到的只有 `JsonParamCodec.decodeObject` 和 `_splitFieldNames` 两处
—— 其余（取主键、读基线合并、调 create）本来就不同，没有硬凑。
