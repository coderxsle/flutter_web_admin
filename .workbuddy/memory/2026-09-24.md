#### ⚠️ 收敛带来的行为变更（必须验证）

1. **租户过滤从「无」变成「强制」** —— 现有 4 个单条操作的 `findFirstRow`
   **全都不带租户条件**（只有 `deleted=false`），`getUserList` 也只在
   `query.tenantId != null` 时才拼。而 `BaseService` / `QueryEngine`
   **无条件**按 `session.tenantId` 过滤。
   方向更正确（现在有租户列却形同虚设），但**回归必须比对 `total`**。
2. **`delete` 必须两步走**：`BaseService.delete` 只收 `id`、拿不到实体，
   **不维护** `updater` / `updateTime`，而原实现会写 →
   先用 `user.update()` 落这两个字段，再 `user.delete()` 软删。
   ⚠️ **顺序不可颠倒**：`CrudService.update` 里有 `setDeleted(data, false)`，
   先软删再 update 会把 `deleted` 复位成 `false`。
3. `delete` 会多走一次审计（默认 `NoopAuditService`，**不落库**）
4. `create` / `update` 统一 `setTenantId(resolveTenantId(session))` ——
   优先 `session.targetTenantId`，旧代码直接用 `session.tenantId`

#### 两个易踩的差异点（已写进代码注释）

- `QueryEngine` 在 `sort` 为空时**不做任何排序** → 必须显式传 `sortAsc('id')`，
  才能保住旧实现的 `orderByList: [t.id.asc()]`
- `QueryEngine` 的 `safePageSize` 上限是 **200**（旧代码 100）→
  必须先用 `buildCrudQuery` 收敛，否则会被放大

### 关键设计点（8 条）

1. ⚠️ **路径参数名必须沿用 `:id`**。`/api/role` 挂载点已被 A 档占着、有 `/:id`；
   `PathTrie._build` 在同一层遇到不同参数名会**在注册阶段**抛
   `Conflicting parameter names at the same level` → **服务根本起不来**
   （报错是 `Segment no 3: ":roleId" is invalid`，离真正原因很远）。
2. ⚠️ **字面量段优先于参数段**（`PathTrie.lookup`）：`GET /api/user/info` 命中
   `info` 字面节点，不会被 `GET /api/user/:id` 吃掉。反过来说，哪天把 `info` 改成
   `:tab` 就会被抢走，表现为运行期 400（不是 404），很容易误判。
3. ✅ **嵌套本身是安全的**：`PathTrie.attach` 是**合并**子路由（不是嵌 router），
   `/:id/menu-ids`（两段）与 `/:id`（一段）不可能互相匹配，也不会 `Conflicting values`。
4. ⚠️ **`RestActionRoute.handleCall` 在 handler 正常返回时一律给 200**，

## S6 —— 后端自动 CRUD 改成「团队式」（2026-09-24，用户拍板）

**触发**：用户自己把 `gi_demo_admin/src/apis/base.ts` 改成团队惯用写法，要求「**把后端自动生成的 CRUD 的 API 也改一下**」。

### 定稿契约（旧的原生 REST 8 条全删）

```
GET  {base}/getList?page=&pageSize=|size=&<filters>   列表
GET  {base}/getDetail?id=123                          详情（id 走 **query**）
POST {base}/add                                       新增（201，body 平铺）
POST {base}/update                                    更新（body 平铺且自带 id，PATCH 语义）
POST {base}/delete        body {"id":1}   → boolean   单条删
POST {base}/deleteBatch   body {"ids":[1,2]} → CrudBatchResult
```

删掉的东西：`GET /`、`GET /:id`、`PUT|PATCH /:id`、`DELETE /:id`、`DELETE /`，以及
`updateMethods` / `enablePostAliases` 两个构造参数与 `_PostUpdateRoute` / `_PostDeleteRoute` 两个类。

### 两个必须记住的语义变化

1. **`enableCreate: false`（现状只有 `/api/role`）→ `POST /api/role/add` 是 404，不是 405。**
   旧版 `POST /` 关掉是 `MethodMiss`（路径还在、方法不允许）；现在 `/add` 是独立路由，
   不注册就是 `PathMiss`。离线断言里凡是断言 405 的都改成了 404。
2. **A 档挂载点下不再有 `:id` 参数段**（`GET /api/user/5` = 404）。
   于是 `PathTrie` 的「同层参数名必须一致」约束只剩**动作路由之间**会触发
   （`/api/role/:id/menus` vs `/api/role/:roleId/users`），测试用例已按这个新场景改写。

### 分页信封（用户贴 JSON 定的形状）

```json
{"code":20000,"message":"","data":{"records":[…],"total":15,"page":1,"pageSize":10,"totalPage":2}}
```

⚠️ **刻意与 typed(8080) 不一致** —— typed 侧 `PageResponse.toJson()` 把元信息摊在顶层。
分歧只在 REST 侧，由 `ServerpodEnvelopeBuilder` 一家收口，`flutter_web_shared` 一行没动。

⚠️ **收口处的顺序陷阱**：`success()` 里 `data is PageResponse` 的守卫**必须在
`data is CommonResponse` 之前** —— `PageResponse extends CommonResponse`，顺序反了会走进
「防双层信封」分支，形状退化成 `data` 是数组。两条支路（`page(RestPage)` 与
`success(PageResponse)`）折成同一形状这件事，已由 `serverpod_envelope_test.dart` 钉住。

### 批量删的返回值

`removeBatch` 契约从「`Map` 里三个计数」升级为返回完整 **`CrudBatchResult`**
（`total/successCount/notFoundCount/successIds/failedIds`，`implements SerializableModel`）。

- 泛型层默认实现改成**逐个 try/catch**：`RestApiException` 且 `httpStatus < 500` 才记 `failedIds`，5xx `rethrow`
  （旧版首个失败就中断 → 一个坏 id 让整批删不掉）。
- 5 个 Service（dept/role/menu/dictCode/dictData）的批量删返回体统一改为
  `CommonResponse.success(batch)` 直接交 `CrudBatchResult` —— 之前只抄 `{'total','successCount'}`，
  导致 `successIds`/`failedIds` **恒为空数组**（前端「N 条不存在」的提示就是这么没的）。
- `rest_delegate_utils.dart` 新增 `batchOf()`、`countOf()` 补 `CrudBatchResult` 分支
  （少了这一支，`ensureDeleted` 会**恒判 404**，因为 `CrudBatchResult` 不是 `Map`）。
- `extractSingleId`（新增）：单条删只接受**恰好一个** id，给多个直接 400
  「多条请用 POST /deleteBatch」—— 因为两者返回类型不同，混成一个入口会让返回类型摇摆。

## 排查：`status=''` 也只看正常用户 —— 是**模型默认值**在顶，光改前端修不掉

用户报：`GET /api/user/getList?...&deptId=1&status=` 只返回正常用户，禁用用户不返回；
并建议「前端在 status 为空时不拼这个参数」。

**实测（`/tmp/probe_user_status.mjs`，真实 HTTP）**：

| 请求 | total | 出现的 status |
|---|---|---|
| `deptId=1 & status=`（前端现状） | 12 | `[1]` |
| `deptId=1`（**完全不传 status**） | **12** | `[1]` ← **用户的方案在这里失效** |
| `deptId=1 & status=1` | 12 | `[1]` |
| `deptId=1 & status=0` | 1 | `[0]` |
| `deptId=1 & status=2` | **0** | `[]` |
| `deptId=1 & status=null` | 12 | `[1]` |
| 无 deptId & `status=` / 不传 | 15 | `[1]` |

**两层根因（缺一不可）**：
1. **模型默认值**：`user_list_request.spy.yaml` 里 `status: String, default = '1'` →
   生成代码 `status = status ?? '1'`（`user_list_request.dart:30`）。
   ⇒ `queryString('status')` 对空串返回 `null`，但构造函数立刻把它顶回 `'1'`。
   **所以「前端不拼这个参数」根本没用** —— 这是用户没料到的部分。
2. **唯一的无条件过滤**：`user_service.dart:211` `condEq('status', int.tryParse(query.status) ?? 1)`
   直接塞进 `filters`，不受任何 `isNotEmpty` 保护。

**其他 5 个资源全部是「空值不过滤」，user 是唯一的例外**（对齐即可，不是发明新语义）：
`dept_service.dart:32-33`、`menu_service.dart:286-287`、`dict_service.dart:91-92` / `:361` 都有
`if (status != null && status.isNotEmpty)`（dictData 是 `if (status != null)`）。

**⚠️ 顺带发现**：`status=2` 返 0 条是对的（`tryParse('2')=2`，库里没有 status=2）——
「解析失败回落 1」只对**无法解析**的串生效（`status=abc` 会静默退化成「只看正常」）。
而 dept/menu 的写法 `t.status.equals(int.tryParse(...))` 遇垃圾串会变成「匹配 NULL」→ 0 条。
两种口径不一致，属于可选清理项。

**改动会翻掉已记录的基线**（都是本次要一起更新的）：
`docs/rest-api-layer.md` L139（回归基线 `user` 无 deptId→15 / `deptId=1`→12）、
L618（`total=15`，注释「是 `status=1` 的行数，**不是** 16」）、L619（`total=12`）、
L664（跨租户 `total=15`）；MEMORY.md 里的「无 deptId 的 total 是 **15 不是 16**」。
修正后应为：无 deptId → **16**（15 正常 + 1 禁用）、`deptId=1` → **13**（12 + 1）。
DB 事实：dept1 子树 12×status=1 + 1×status=0；全租户 15×status=1 + 1×status=0。

**未动手** —— 已把方案交给用户选（涉及口径变更 + 基线翻新，不擅自动）。
